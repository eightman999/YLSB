# v0.3 から v0.4-rc3 への移行

v0.3 の frozen/raw/normalized/derived は履歴として保護する。移行はコピーや上書きではなく、adapter が v0.3 observation を読み、v2 grader と v0.4 fixture metadata を付加して `results/v0.4-rc1/` に派生物を作る。

## identity と version

- source fixture: v0.3 の fixture id/version/hash。歴史的入力の由来を示す。
- `fixture_v04`: `fixtures/v0.4-rc1/` の明示 metadata。tier、gate role、修正版 constraint-003 を示す。
- `grader_identity`: `common/grader_basic.py` v2 と SHA-256。
- `provenance`: source、adapter method、legacy provenance を保持する。

修正版 `CORE-CONSTRAINT-003` は v0.4 では正しい gold を持つが、v0.3 の誤った gold を再計算で歴史修正しない。v0.3 row は `FIXTURE_INVALID` として能力分母から除外し、v0.4 row は別 fixture として検証する。

## 決定論的な再生成

依存する JSON Schema validator を先に導入する。

```sh
python3 -m pip install -r requirements-v04.txt
python3 tools/regenerate_v04.py
python3 tools/regenerate_v04.py --check
```

この一つの生成器が fixture validation、migrate、regrade、calibration、planner、schema mirror、manifestを同じ一時treeへ出力する。`--check` は既存の生成treeを変更せず、再生成との差分があれば非0で終了する。manifestは入力corpus、fixture、policy、grader、planner、registryのcontent hashとrecord countsを記録し、HEADや生成時刻のようなvolatile値は保存しない。

`regrade` は入力 corpus の `task_results.jsonl` と同じ bundle にある performance/runs を参照する。別 bundle の値や ROOT の固定性能値へフォールバックしない。TG は phase、point、lane、context が揃う repeat の mean で、candidate と observed formal slot を JSONにも保存する。

v0.4 を新規実行する場合は `fixtures/v0.4-rc1/` と `policies/ylsb-v0.4-rc1.json` を明示指定する。既存 course profile は v0.3 のままなので、profile名だけで v0.4 fixtureへ暗黙移行しない。

## baseline と release

v0.3 protected file の恒久検査は `fixtures/v0.3-baseline-hashes.json` を使う。公開済みの履歴は変更せず、現行の生成結果は `results/v0.4-rc1/manifest.json` の engine release と content hashを正とする。
